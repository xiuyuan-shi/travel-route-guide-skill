# 网页发布与访问验证

用户要网页分享时，先检查本任务的部署记录和已经授权的可用渠道。复用站点，不探测无关账号或搜集凭据。用户选定的服务优先；没有可用渠道则先完成可交付HTML和发布包，再只询问缺少的账号／域名信息。

不要把一次 `chatgpt.site` 被拦截推广成所有站点都不可用，也不要承诺 GitHub Pages 在所有网络可达。

## GitHub Pages（有已登录 gh 且公开托管在请求范围内）

- 仓库公开也会公开文件和提交信息：只放此攻略产物及必要许可文件，不放票据截图、坐席、订单号、工作笔记、配置凭据或聊天记录。若仓库仅含本次已授权公开的静态攻略，按既有授权继续；如还涉及未授权公开的额外源码或资料，先移出发布包，确有必要公开时再确认。
- 查看现有仓库和 Pages 配置。新仓库只创建一次；仅对用户拥有／授权的仓库操作。
- 静态 index.html 与 `.nojekyll` 放发布根目录。Git 使用现有认证；普通 push 缺 helper 时可用单次 `git -c credential.helper= -c 'credential.helper=!gh auth git-credential' push`，不打印或写入 token。
- 通过当前 GitHub 官方文档核实 Pages API；首次设置分支根目录发布，之后 push 并等待当前提交构建完成。
- 记录 repo、实际 html_url、目录和发布提交到本任务工作文件，以便下次更新。不要把用户账号或具体 repo 固化到 Skill。

## Sites（当前环境可用时）

使用可用的 Sites 构建／托管技能及工具契约；不要在本 Skill 复制会漂移的接口细节。若本地配置含 project_id，保持原样复用。只部署已保存版本，遵守当前访问权限和用户要求的分享范围；短期凭据不得入库。

## 发布验证与故障边界

1. 等待发布成功，核对部署关联当前版本／提交。
2. 从无 Cookie、无 Authorization 的请求读取公开网址，检查真实标题、最新文案和数据，而不是仅检查状态码。
3. 用浏览器看页面、地图与分享按钮，确认分享地址不是 localhost、file:// 或旧站点。
4. 用户要求微信／特定网络可达时，不能只用本机浏览器作为证据。交付新地址并请其在原受影响环境验证；说明已验证范围。
5. 403／安全拦截若发生在应用前，检查公开权限、运行日志、网络响应。不要反复改前端代码或分享账号令牌。已公开仍受托管边缘限制时，可在授权范围内迁移渠道；PDF只是额外备份，不等于网页问题解决。

不要替用户向朋友发消息，除非明确授权；生成分享按钮本身不代表已发送。
